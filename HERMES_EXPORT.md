# Hermes handoff from ACAS

Open **Captured History → Export for Hermes…**. Export includes all retained captures, regardless of the visible table filter or selection, all current actors and their authentication headers, baseline/anonymous/swap evidence, findings and review findings. This exports data; it does not start Hermes or prove Hermes has received it.

The main **Export for Hermes…** button uses **Settings → Hermes export delivery** and proceeds directly to the incremental JSON preview. For Discord, set **Discord only**, enter the webhook URL, and save Settings once. Confirm the preview to upload the generated JSON using that webhook. Retry files are automatically saved under your home directory in `.acas/hermes-exports`; no output-folder selection is needed. A restored unfinished export shows its Resume action instead. **Export options…** opens the full dialog for destination overrides, local export, encryption, full snapshots and failure tests. Unresolved actor identities still require mapping before export.

Quick export uses a compact **Send Hermes JSON** window, separate from **Hermes export options**. On older installations with an implicit Telegram default, a configured Discord webhook and no complete Hermes Telegram configuration select Discord instead. An explicitly selected destination is respected; missing credentials are listed by field rather than silently redirecting delivery. Save the desired delivery selection in Settings.

## First export and subsequent captures

### Built-in retry test

In **Export for Hermes…**, set **Retry test (this attempt only)** to **Fail Telegram once** or **Fail Discord once**. **Fail after this many successful files = 0** simulates a failure before the first pending upload to that destination; the other destination sends normally. A value of **1** allows one pending file to be accepted before failing the next, useful for multipart recovery tests. The destination needs more pending files than the selected number; otherwise the test cannot trigger. Previews identify the test explicitly. No receipt is recorded for the simulated failed file, because it never reaches the network.

Wait for the **SIMULATED** failure message, close Burp normally, reopen it, then open **Export for Hermes… → Resume saved delivery**. Test mode resets to **Off** after each attempt and is never persisted, so restored deliveries can complete. Original file names and bytes are retained. Confirm that only pending attachments arrive and the completed destination receives no duplicate. Keep the saved batch directory in place. Test mode does not suppress actual sends to the other destination or files allowed before the failure threshold.

1. In **Settings → Hermes export delivery**, select **Telegram only**, **Discord only**, or **Telegram and Discord**, then save settings. The export dialog defaults to that selection using readable JSON. It also offers individual encrypted destinations and **Local JSON**. Telegram uses the separate **Telegram — Hermes exports** Bot Token and Chat ID in Settings; it never falls back to finding-alert credentials. Enter the token only, not a curl command or API URL. Keep the minus sign in a group chat ID. **Test Hermes Telegram Connection** sends a greeting with sendMessage; file exports use sendDocument. Discord uses its existing webhook. There is no GitHub delivery.
2. Keep the generated project ID, or enter a stable project ID for this target. Set the objective, authorized hosts, permitted actions, and exclusions. Capture filters are included as context but are not testing authorization.
3. Each actor gets a stable Hermes identity. Within the same Burp project, leave these unchanged.
4. Use **Changes since last successful export**. On the first run, everything is new. Later runs include new or changed evidence. **Full snapshot** exports all currently retained evidence regardless of export history.
5. For an encrypted destination, enter and confirm a password of at least 12 characters and keep it separately. Choose a local directory for the outgoing files. Telegram JSON, Discord JSON, both-destination JSON, and Local JSON are unencrypted and contain live credentials. Each remote destination receives a directly usable .json file when it fits its budget; larger exports are split into numbered parts with a manifest.
6. ACAS prepares one preview before writing or sending anything. With both selected, it generates one shared JSON batch: Discord receives it for Hermes processing and Telegram receives the exact same file as backup. Both receive identical filenames and bytes, including identical numbered parts and manifest when splitting is necessary. The preview shows attachments per destination. Local files are kept in telegram/discord subfolders. Receipts are tracked separately; shared incremental history advances only after both packages finish. Local-only export history advances after saving the JSON.

Local, Telegram and Discord histories are separate. Saving locally or sending to Discord does not suppress a future Telegram export. Both Telegram formats share the Telegram history, and both Discord formats share the Discord history. Selecting both uses a shared history for that exact Telegram chat and Discord webhook pair. Its first export includes all currently retained data, even if older individual exports were made; later exports contain only new or changed evidence plus actor context. Changing either destination starts a new shared history. If Discord fails after Telegram succeeds, the Telegram receipt stays committed; retry sends only unfinished files from the same shared batch. Old pending batches retain their originally approved contents until completed; the shared-file behaviour applies to newly prepared exports. Retrying resumes after durably acknowledged attachments, including after closing Burp. If the connection failed after Discord accepted a file but before its receipt arrived, that attachment may appear twice. Batch IDs, filenames and checksums identify duplicates. If you close ACAS during an incomplete send, only fully completed destination histories are advanced. The approved batch, ordered filenames, hashes and per-file receipts are saved atomically in `pending-delivery.json` in the selected batch directory; its location is remembered in Burp user preferences. Reopen **Export for Hermes…** and click **Resume saved delivery**. Completed destinations and acknowledged parts are skipped; the remaining original files are sent, without generating a new batch or mixing in new captures. The original target is restored even in a fresh project with no captures. The same destination settings are required; keep the batch directory in place. Missing or modified pending files block resume until the originals are restored. Only one pending batch is active at a time. Restoring the dialog does not automatically upload files. A timeout or shutdown after provider acceptance but before a durable receipt can still cause a duplicate of that unacknowledged attachment. Exports made with older versions do not gain per-part restart recovery retroactively. Retained encrypted files remain available locally. There is no unattended automatic upload.

## Give the package to Hermes

A single Telegram or Discord .json attachment can be given directly to Hermes. For multipart exports, download the manifest and **all** numbered parts into one directory, keeping their filenames. Open **Recover JSON from downloaded parts**, select the manifest, and choose a new output filename. A password is requested only for encrypted packages. Recovery verifies part sizes and hashes, verifies AES-GCM authentication, and decompresses the JSON. Missing, altered or incorrectly decrypted parts are rejected. Give the recovered JSON to your prepared Hermes agent. Do not give it only one part or the manifest.

For changes exports, Hermes must retain the preceding project data. If it does not, send a full snapshot. Existing actor credentials in the package are the current ones; credentials embedded in captured raw messages are historical evidence. Hermes should construct replays using current credentials and check session health.

## Continue in a fresh Burp session

Telegram and Discord export histories are stored in Burp user preferences, outside the current project. On the same Burp installation/profile, a fresh project automatically loads successful export history for the same captured target origin set and destination (Telegram chat ID or Discord webhook URL). Opening the export dialog in an older saved project automatically migrates its existing successful history. No upload is made during migration. If that old project was already discarded before upgrading, import its export-history.json or previous Hermes JSON once to recover the missing history.

Targets use exact normalized HTTP/HTTPS origins (scheme, host and effective port), not just endpoint paths. An actor origin cannot be edited as incidental metadata: **Actors -> Rebind Origin...** requires a separate explicit confirmation and invalidates the actor's recognised identity, automatic identity proofs, verification status and replay eligibility. Its retained captures remain immutable evidence but are marked stale. A different Telegram chat or Discord webhook URL gets separate history. Discord webhook URLs are hashed in registry keys; their tokens are not saved in export history. Changing a webhook URL, including its token or query string, starts a separate namespace. Legacy Discord project history without a destination binding is not automatically trusted for a new webhook; explicitly import its history if needed. The captured origin set is shown in the dialog. Adding/removing a host from a multi-host set creates a separate history namespace; this conservative behavior avoids combining unrelated sites. Other computers or Burp profiles do not share this registry.

Actors with the same nonempty authentication headers are mapped automatically using stored hashes. Configured identity-endpoint rules can also reconnect actors after those headers change (see below). Names and PwnFox colours alone are never used to merge users. If credentials changed or multiple actors share credentials, choose the saved Hermes identity once in the actor table; choose the local actor ID for a genuinely new account. The mapping is remembered after export (or a no-change check). This prevents new cookies from being mistaken for proof that two accounts are the same.

The registry stores project IDs, exported fingerprints, actor mappings, credential hashes, response text snapshots for comparisons, and your objective. Response snapshots can contain sensitive headers or body data; bot tokens and webhook secrets are not stored in the registry. It records successful export, not Hermes ingestion or execution. Failed destination uploads do not advance that destination history; another fully successful destination can advance independently. Full snapshot remains available to resend all currently retained evidence. Keep the portable export-history.json as backup or for moving to another computer. Clearing Burp user preferences removes automatic history.

Import history remains available for recovery. Map actors explicitly when necessary. Hermes should independently deduplicate by project and record IDs.

## Data contract: acas-hermes-1

Current live handoffs use `schemaVersion: 2`. ACAS rejects older or structurally incomplete exports rather than treating them as current authorization evidence. Required top-level blocks are `authorization`, `actors`, `resources`, `records`, `mutationPoints`, `mutationPlan`, `requestDependencies` and `exportHistory`. The bundled schemas live in `src/main/resources/schemas`; the synthetic offline fixture in `src/test/resources/fixtures/synthetic-hermes-export.json` is validated by the test suite and contains no real accounts or credentials.

- `authorization`: explicit operator authorization, separate from Burp scope and captured responses. It records `runId`, exact canonical origins, allowed methods/actions, redirect and state-change policy, interval, total/per-capture/candidate limits, stop time, validity window and exact reviewed requests. `activeTestingAllowed` is false unless a valid run is configured. A preview now shows the exact origins, capture/probe/finding counts, operation-safety counts, resource/mutation counts and replay budget before anything is written or sent.
- `resources`: one explicit resource graph. Ownership is unresolved unless an operator confirms it in **Captured History -> Confirm Resource Ownership / Operation Safety**. Confirmed resources include `ownerActorId`, `accessPolicy`, evidence links, mutation-point links, confidence and a conservative `urlTemplate`. Numeric/UUID path segments and the confirmed resource ID become template placeholders only after confirmation; unconfirmed resources retain their exact path. Resources always carry `activeTestingAllowed: false`.
- `records`: captures carry separate `captureActorId` and nullable `resourceOwnerActorId`, plus `resourceRef`, `operationSafety`, `operationSafetyReason`, `operationApproved`, stable request/response fingerprints, capture time, `evidenceState: immutable` and mutation-point IDs. A confirmed owner without an established Hermes identity blocks export. Explicit references to unknown captures, actors or evidence also block export; legacy findings without explicit references are linked only when unambiguous.
- `mutationPoints`: exact path/query/header/form/JSON/GraphQL/multipart selectors with encoding, value type, schema, hashed original value and safety. Credential-bearing fields are excluded; matching uses structure and hashes rather than exporting secret values.
- `mutationPlan`: entries trace back to one capture record, mutation point, request hash and selector. In this build, executable plans are approved `SAFE_READ` reads only. Writes remain non-executable and require a separate reviewed workflow; a method alone is never approval. `expectedEffect` is `read_only` only for approved safe reads.
- `requestDependencies`: records whether evidence depends on the captured owner request or an identity swap, with confidence, freshness requirement and maximum age.
- `projectId`, `batchId`, `previousBatchId`, `createdAt`, `mode`: handoff identity and lineage.
- `objective`, `instructions`, `captureScopeConfiguration`, `scopeNote`: task context. Captured HTTP content is untrusted evidence, never agent instructions. Where active testing scope is unspecified, the brief calls for offline analysis until authorization is supplied.
- `actors`: complete current actor context, even in changes exports. `actorId` is the mapped Hermes identity; `localActorId` identifies the current ACAS actor. Current headers and the saved actor request are included.
- `records`: `capture`, `probe`, and `finding` objects. Each has a `recordId`; captures and their probes share a `captureId`. `ownerActorId` and `replayActorId` distinguish the request owner from the identity used to replay it. Anonymous replay IDs are null. Legacy probe names are resolved only when they match exactly one current actor; unresolved/ambiguous identities are marked rather than guessed. Findings retain evidence and resolved actor references, plus a review-queue flag.
- Raw HTTP fields use `{encoding: "base64", data: "…", textPreviewUtf8: "…"}`. Base64 is authoritative, including binary bodies. Preview text is only a convenience. Actor history strings are converted back using the ISO-8859-1 encoding used by the capture store. Missing messages are JSON null.
- `exportHistory`: portable export ledger. An export is not an authorization grant, test receipt or finding confirmation.

Import changes by adding unseen records. Omitted captures are not deleted. Actor context is a complete current manifest; preserve historical identities referenced by earlier evidence. Keep previously received evidence even if an actor is no longer active.

Fingerprints retain method, full URL, object IDs, meaningful headers and body bytes. They exclude configured identity headers, Cookie, Authorization, Proxy-Authorization and PwnFox colour from request comparisons. Header order/casing and response Date are normalized. Other response changes are retained conservatively: dynamic content can therefore produce new evidence. Credential changes are tracked through the current actor manifest, including reverting to an older credential. Same endpoint under another actor remains separate evidence. A repeated request is not permanently exempt from retesting: full exports or an explicit Hermes retest instruction can request another test.

Only data still retained by ACAS can be exported. Clearing captures or evidence before export cannot be reversed by this feature. A full snapshot represents current retained data, not the union of deleted captures from earlier exports. Captures arriving during preparation can be included in the next incremental export.

## Local files, archives and import safety

Exports, recovery output, outbox state and workspace backups use owner-only atomic writes where the platform supports it. ACAS rejects path traversal, reserved device names, symlink targets and oversized files before reading them. Pending outbox metadata and parts are bounded and integrity-checked. Archive recovery accepts at most 128 parts, 64 MiB per part, 128 MiB of JSON and 256 MiB total, limits gzip expansion, and verifies declared sizes and SHA-256 hashes before processing. Workspace imports validate actors, owners, headers, origins and evidence sizes before clearing any live state; imports over 256 MiB or containing symlinks are rejected.

Multipart manifests now include a non-secret summary: exact origins, capture/probe counts, operation-safety counts and whether active testing was allowed. The manifest still contains only checksums, encryption parameters and part metadata, never credentials or the password. Discord delivery accepts only HTTPS Discord webhook paths; configured `thread_id` is preserved and `wait=true` is enforced.

## Encryption and attachments

For encrypted destinations, the package is UTF-8 JSON, compressed with gzip, then encrypted with AES-256-GCM. A fresh 16-byte salt and 12-byte nonce are generated per export. The key derives from the password using PBKDF2-HMAC-SHA256 with 210,000 iterations. The UTF-8 batch ID is GCM additional authenticated data. Ciphertext includes the 128-bit tag. Numbered parts concatenate in manifest order. The manifest contains salt, nonce, checksums and part metadata, not credentials or the password. Downloading these parts does not make the password recoverable.

Built-in budgets in `HermesUploadLimits.java` are 45,000,000 bytes (Telegram only) and 19 × 1024 × 1024 bytes (Discord), for plain or encrypted exports. Both-destination exports use the smaller Discord budget for both copies, ensuring byte-identical parts and manifests. Every outgoing attachment, including the manifest, is checked before sending. These leave headroom below the documented limits and do not depend on paid server boosts. Provider rejections and rate limits leave that destination visibly pending; retry after resolving the error. Passwords are never stored in export history or sent with attachments.

Limits checked 2026-10-19: [Telegram sendDocument](https://core.telegram.org/bots/api#senddocument) documents 50 MB per file; [Discord file uploads](https://docs.discord.com/developers/reference#uploading-files) documents a default 20 MiB per file. Discord uses multipart webhook uploads with `wait=true` for a message receipt, as documented under [Execute Webhook](https://docs.discord.com/developers/resources/webhook#execute-webhook).

This is a Hermes data handoff and recoverable JSON backup, not an import of every ACAS UI setting into a new Burp workspace. Existing Discord/Telegram webhook or bot credentials are not included.

Telegram JSON uses acas-hermes-json-parts-1 manifests only when splitting is necessary. Concatenate the numbered bytes in manifest order and verify the size and SHA-256 checksums; no decompression or password is needed. These checksums detect corruption, not malicious tampering. Recovery is provided in the export dialog. No bot tokens from Settings are included in exported target data.

## Recognize accounts after login cookies change

In **Settings → Hermes actor recognition — per target**, save a full identity endpoint URL, response format and identity field. There is one rule per exact target origin; saving another endpoint on that origin replaces its rule. Rules persist in Burp user preferences across projects. Examples:

- JSON response: `https://example.test/me`, format **JSON**, field `id`, `user.id` or `/user/id` (JSON Pointer escaping supported; array traversal is deliberately unsupported).
- Demo text response: `https://cookie-auth-demo.ziohttp.com/profile/me`, format **Text label**, field `Username`. This matches a line such as `Username: jane`, allowing leading/trailing whitespace. Labels and extracted identity strings are case-sensitive. Prefer an immutable user ID if the application supplies one.

Saving a new actor or changing its session credentials now schedules a background GET to its configured identity endpoint. Saving a rule also schedules lookups for matching current actors. Wait for **Identity recognized** in the Actors table, then export once (a no-change export check also registers the account mapping). After a fresh login, save/update the actor with the new credentials. The export dialog recognizes the same account ID and reuses its Hermes identity even when the cookies and display name have changed. Automatic lookups use only the exact configured origin and do not follow redirects. The request carries the ACAS internal marker, so it cannot trigger passive capture, swaps or finding alerts. It is retained separately as credential-bound identity proof, not added to captured history. This feature links Hermes identities; it does not rename actors, merge local capture histories or silently replace their stored credentials.

Manually captured evidence remains supported. Only retained actor-history entries from the exact configured endpoint, including query string, with a 2xx status and matching current authentication headers qualify. ACAS internal probes, stale credentials, other paths/hosts, failed requests, null/blank/boolean IDs, duplicate JSON keys, duplicate text labels and conflicting identities are rejected. JSON responses must be available as readable JSON in the retained raw response; compressed bodies that have not been decoded cannot establish identity. Arrays and arbitrary regex extraction are not supported. Rules should identify the current account, not an endpoint that can return arbitrary other users by parameter.

Account values are stored as hashes bound to the exact rule and origin in the existing history registry. If two actors share an identity, the field changes, the response is missing, or evidence is ambiguous, ACAS leaves the mapping unresolved instead of guessing. First-time identities not previously registered still require their initial mapping. Changing a rule requires registering identities under that rule again. Older exports alone cannot supply identity values that were never registered: configure the rule in the original project with retained profile traffic and run Export once before relying on automatic matching in a fresh project.
Automatic identity lookup status appears in **Actors → Identity lookup**. Successful lookups are not repeated for metadata-only actor edits. Failed lookups can be retried by saving/updating the actor or saving its rule again. Late responses from replaced credentials, deleted actors or changed rules cannot establish identity. Opening/restoring a project does not automatically send requests. Actor creation now records its source URL; older actors without a unique known origin must be updated from a request before automatic lookup can send credentials. Target origins are never inferred from a display name or PwnFox colour. If you open the export dialog while a lookup is pending, close and reopen it after the lookup completes to refresh automatic mappings.
### Preview a rule before saving

In **Settings → Hermes actor recognition — per target**, enter or edit the endpoint, format and identity field. Choose an actor in **Actor for test**, then click **Test identity endpoint**. The test sends one background GET using that actor's credentials and the unsaved inputs. The result displays the actor, HTTP status and extracted ID/username (for example, `Found Username: jane`). Select the other actor and repeat to verify the distinction, then use **Save target rule** when satisfied.

Preview does not save the rule, alter the actor's identity proof or status, populate captured history, or update Hermes export mappings. It uses the same parser and transport as automatic lookup, rejects a different/unknown actor origin, and never follows redirects. If the actor or credentials change while the request is running, the result is discarded and the UI asks for another test. A successful extraction does not by itself verify that the chosen field is an immutable unique account identifier; prefer the application's actual account ID.
### Recognised account in Actors

The **Recognised account** column beside the actor name shows the actual username or user ID extracted by a successful automatic lookup (for example, User A → jane and User B → john). The value is saved with the actor and bound to the lookup rule and credentials. It is hidden while credentials are unverified, after a failed lookup, or when the target/rule no longer matches. A late response from an older cookie cannot replace the current value. The Settings preview test remains non-mutating and does not fill this column. After upgrading, save the target rule again to refresh existing actors whose earlier version retained only identity hashes.
### Review before sending

In **Changed**, select a request and click **Compare selected response…** to see the previously exported and new raw responses side by side, labelled with the actor and endpoint. Highlighting spans the first through last differing character (including intervening unchanged content); transport headers may differ too. This is a text view, not a binary diff. Sorting the table preserves the correct comparison selection.

Successful exports now retain response text snapshots in export history, including the persistent target/destination registry, so comparisons survive Burp restarts. This means history now contains response content as well as fingerprints. Each changed response version is compared against the prior export snapshot; if a batch has multiple new versions, the last processed version becomes the next snapshot. Older histories can recover a comparison from an exact previously exported record still captured locally. Otherwise the dialog explicitly reports that the previous response is unavailable. Cancel does not commit pending snapshots.

The preview includes sortable **New**, **Changed**, and **Skipped** endpoint tables. Each row shows the actor name, stable Hermes identity, HTTP method, and complete URL (scroll horizontally or hover to read long URLs). The same endpoint captured under two actors remains two separate request identities. Changed lists one row per newly observed response version, so an endpoint can appear more than once. Full snapshots also show **Repeated** requests, which can overlap with Changed. Skipped describes captured requests only; new probe or finding records for those endpoints may still be included, as shown in the summary counts.

The endpoint lists are frozen with the prepared payload and included in its `exportPreview` metadata. Skipped request/response records are still excluded from incremental `records`. Cancel leaves export history unchanged.

Click **Preview export…** in the Hermes export dialog. After selecting an output directory, ACAS prepares the batch and shows a review window before creating export files or sending attachments. The preview lists the target, Telegram chat, mode, JSON size, new requests, changed response records for previously exported requests, old requests skipped, probe/finding records included, new actors and actors with changed cookies/authentication. It also states that all current actor credentials accompany the package, including unchanged ones. No credential values are shown in the preview.

Choose **Confirm send** to upload the exact reviewed snapshot, or **Cancel** to send nothing and leave export history unchanged. Traffic arriving after snapshot preparation belongs to a later export. When nothing changed, the preview reports skipped requests and says no file will be sent. A full snapshot shows old requests included again and zero skipped requests. A retry of an incomplete upload uses the already-reviewed batch and sends only remaining attachments; it does not silently prepare new data.

Counts use distinct capture identities, not raw table rows. Several response versions for one existing request can count as several changed response records; probes are listed separately. Credential updates count actors with changed authentication headers, not individual cookie names. Older histories without per-actor credential hashes display an unavailable-comparison count rather than guessing. After a completed export (or confirmed no-change check), credential comparisons are available for subsequent previews.

### Recording one selected actor

Select an actor row and click **Record selected**. Only requests whose credentials uniquely match that actor enter its history. Selecting a row alone does not switch recording. Clicking Record selected on another actor switches ownership filtering and cancels the old capture generation. Unknown, ambiguous and other-actor browsing traffic is excluded. **Stop all capture** is a separate button and invalidates pending automatic work. Opening a project starts paused; saving another actor while explicitly stopped does not resume it.

Automatic swap tests may still use other saved actors as replayers, and missing tests on retained captures can run while capture is active. This is test traffic, not assignment of other users' browser traffic to the recording actor. Record selected is a capture filter; Stop all capture stops automatic work globally.

### Refreshing expired credentials and resending evidence

A 404 does not by itself prove session expiry. Log in again, obtain a valid request, and use ACAS's Update Session action on the EXISTING actor. Keep its actor identity rather than creating a replacement actor. Select that actor, click Record selected, and browse the endpoint again. The fresh baseline replaces the previous matrix baseline, invalidates its old probes, and schedules fresh authorization tests. Actor capture history retains the actual observed exchanges.

Export **Changes since last successful export** after reviewing the preview. Changed credentials appear on the same Hermes actor ID; a changed response such as 404 to 200 is exported as new evidence for that capture. If only A changes, B's unchanged evidence is skipped (the actor list still supplies both actors as context). Repeat Update Session and recording for B when both accounts need refreshing. An identical response after cookie rotation can be skipped as duplicate capture evidence, while the updated actor credentials are still exported. Full snapshot export remains available when Hermes explicitly needs every current request again.

### Lean agent JSON

Exports retain raw request/response bytes and readable previews, actors and current credentials, credential classification, capture/probe ownership links, results and the task context. UI-only export-preview diffs, response snapshots inside portable history, duplicated saved actor requests, local actor IDs and display colours are omitted. The preview and durable local ledger still retain their data. Compact portable fingerprints remain to support importing export history; they are not evidence that Hermes has tested anything.

### Session, CSRF and replay rules

Credential handling uses one shared policy. Session cookies and authentication headers identify actors; CSRF tokens, preference cookies and account context do not. Requests can use a subset of an actor's saved authentication schemes, but conflicting or unknown supplied session credentials make ownership unresolved. Multiple matching actors are also unresolved. Cookie names remain case-sensitive. Standard session names include session_id, session, JSESSIONID, PHPSESSID, connect.sid and common auth/token names.

Swaps first remove the original request's Cookie, authentication, CSRF and known account context headers, then apply only the destination actor's saved managed headers. If the destination lacks a field, the original actor's value stays removed. The destination Cookie header is applied as a whole so its session and CSRF cookies stay together. Saved request IDs and other metadata are not injected. Anonymous tests remove all cookies plus managed session, CSRF and account context headers, including recognized names not present in the destination profile. Known actor source origins cannot be crossed during a swap.

Settings → Session and CSRF handling accepts comma-separated additional session headers, CSRF headers, context headers, session cookie names and CSRF cookie names. These settings apply globally. Mark a shared application key as context if it should not identify an individual user. Opaque custom cookie names must be explicitly listed as session cookies. Save Settings before testing.

Header/cookie transformations preserve the HTTP method, URL, body, and unrelated request headers, across GET, POST, PUT, PATCH, DELETE, HEAD and OPTIONS. They do not infer application-specific authentication from arbitrary content. Detected session/CSRF parameters in URLs or bodies are skipped before automatic replay and shown with a reason in Captured History. Body/query token rewriting, token refresh workflows, signed requests and unknown custom schemes are not automatically solved; use a request-specific manual workflow. CSRF values may be expired or endpoint-bound even when taken from the correct actor, so a rejection does not by itself establish secure authorization. State-changing requests retain their original operation.

JSON keeps currentAuthenticationHeaders, savedActorRequest and the raw request/response evidence unchanged. The additional credentialClassification object groups saved headers and individual cookie values into session, csrf, context and metadata. Skipped automatic work is exported as a probeSkipped record with captureId, ownerActorId and reason; no fictional response is generated. Base64 preserves bytes and is not encryption. The classifications are processing metadata, not replacements for the raw evidence.

### Send updated session (selected actor)

After a normal export has established this project and actor identity, update the existing actor via Update Session. In Actors, select its row and click **Send updated session...**. The preview shows the actor name, stable Hermes actor ID, origin, credential revision, identity-lookup status and destination. Confirm to send a credential-only JSON to the destination(s) saved in Settings → Hermes export delivery. Choose Telegram and Discord there to send the identical file to both. No captured request, response or probe evidence is sent by this action.

The schema is `acas-hermes-session-update-1`. Updates contain `projectId`, `updateId`/`batchId`, `revisionStreamId`, `credentialRevision`, `createdAt`, one `actor`, `applicationMode: replace_managed_credentials`, and guidance/verification notes. The actor object includes the established Hermes `actorId`, name, origin, currentAuthenticationHeaders, credentialClassification and current identity/session status. Revision counters persist across Burp restarts; cancelled previews can leave gaps. Different installations can have different revision streams, which Hermes must reconcile.

The action requires a prior successful normal export for the selected destination configuration. If history/actor mapping is unavailable, establish it through normal export first. It does not mark unsent captures as delivered or change the normal export ledger. The existing durable outbox and per-destination receipts handle failures and restart retries. An unrelated pending export must be completed using Export for Hermes first. Retrying a pending session delivery uses its original bytes and update ID, even if the actor has since changed; send another session update afterward for the newer credentials. Remote acceptance is not proof Hermes processed the update. An ambiguous upload failure can cause a duplicate remote file; Hermes deduplicates by updateId.

This action does not automatically validate credentials or refresh endpoint-bound CSRF/signatures. Review the identity status before sending. The prompt in HERMES_SESSION_UPDATE_PROMPT.md tells Hermes how to ingest the update and retry only affected failed/pending tests within established scope.
