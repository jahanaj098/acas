# ACAS — Access Control Attack Simulator

## Complete Product Specification and Implementation Blueprint

Version: 1.0  
Prepared for: Engineering / Security Tooling Team  
Date: 2026-03-28

---

## 1. Executive Summary

ACAS (Access Control Attack Simulator) is a Burp Suite extension with an optional companion dashboard designed to automate access control testing through multi-actor simulation, object ownership mapping, mutation-based request transformation, and response-diff driven vulnerability detection.

The goal is to move access control testing away from manual repetition such as changing IDs, switching sessions, and guessing attack paths, and toward a structured system that models real attacker behavior.

ACAS focuses on the classes of issues typically described as:
- IDOR (Insecure Direct Object Reference)
- BOLA (Broken Object Level Authorization)
- Privilege escalation
- Partial data exposure across identities
- Workflow and state-based authorization flaws
- Parser or mutation-based access control bypasses

The tool combines:
- Actor-aware session management
- Automatic object extraction and ownership mapping
- Regex and AST-assisted request/response analysis
- Mutation-driven access control fuzzing
- Automated replay and semantic diffing
- Burp-native workflow integration
- Optional real-time alerting and dashboard visualization

---

## 2. Problem Statement

Traditional access control testing is difficult because testers must manually:
- Maintain multiple authenticated sessions
- Track which user owns which resources
- Identify object-producing endpoints and object-consuming endpoints
- Replay requests with different identities
- Try parser confusion and mutation cases by hand
- Compare responses to determine whether access control was actually bypassed

This leads to common problems:
- Testers lose track of ownership context
- Sessions get mixed up
- Only obvious ID changes are tested
- Complex multi-user attack paths are missed
- Workflow-based authorization flaws remain undetected
- Findings are hard to reproduce and explain

ACAS solves this by turning access control testing into a model-driven simulation system.

---

## 3. Vision

Transform access control testing from:

change ID -> send -> compare manually -> guess

into:

model actors -> map ownership -> generate attack variants -> replay automatically -> diff semantically -> report evidence

ACAS should act like a junior-to-senior tester assistant that continuously observes traffic, learns object ownership, and suggests or executes realistic attacker actions.

## 5. Core Concepts

### 5.1 Actors
Actors are user identities or request personas.

Examples:
- attacker_1
- attacker_2
- victim_1
- victim_2
- admin
- anonymous
- support_user

Each actor stores:
- Name
- Role label
- Cookies
- Authorization headers
- Additional custom headers
- Session validity state
- Enabled/disabled state
- Metadata (notes, tags, source request)

Purpose:
- Replay any request as a different identity
- Compare access rights across identities
- Simulate real attacker-victim scenarios

### 5.2 Objects
Objects are identifiers or resources extracted from requests/responses.

Examples:
- user_id
- order_id
- invoice_id
- file_id
- document_id
- org_id
- team_id
- uuid
- slug

Each object should track:
- Object type
- Object value
- Owning actor
- Source endpoint that produced it
- Endpoints that later consume it
- Confidence score
- Data type (number, UUID, string, array, composite)

### 5.3 Relationships
ACAS tracks relationships such as:
- actor owns object
- endpoint produces object
- endpoint consumes object
- actor accessed object
- mutation triggered finding
- response leaked fields from another actor's object

### 5.4 Mutations
Mutations are transformed request variants intended to expose access control flaws.

Examples:
- Session swap only
- HTTP method change
- Parameter pollution
- Path mutation
- Header injection
- JSON structure mutation
- Case manipulation
- Array wrapping
- Null byte injection
- Version path mutation

### 5.5 Findings
A finding is a structured security result generated by comparing expected authorization behavior with actual response behavior.

Examples:
- Full IDOR
- Partial data leak
- Privilege bypass
- Method-specific authorization bypass
- Parser confusion based access control bypass
- Legacy endpoint auth regression

## 10. End-to-End Workflow

### 10.1 Launch
1. User opens Burp Suite.
2. User loads ACAS extension via Extender.
3. ACAS registers listeners, context menus, and custom UI tabs.
4. ACAS loads previous state if persistence is enabled.

### 10.2 Scope Setup
1. User configures ACAS scope.
2. ACAS may respect Burp target scope.
3. User can additionally define:
- Included domains
- Excluded domains
- Included path regexes
- Excluded path regexes
- Allowed content-types
- Static asset exclusions

### 10.3 Actor Setup
1. User authenticates in browser through Burp.
2. User right-clicks a captured request.
3. User chooses “Save as Actor Profile”.
4. ACAS extracts cookies and auth headers.
5. User labels actor name and role.
6. Repeat for multiple identities.

### 10.4 Traffic Learning
1. User browses application normally.
2. ACAS passively analyzes requests and responses.
3. Regex scanner detects candidate identifiers.
4. AST analyzer parses JSON/XML/GraphQL structures.
5. Node classifier labels likely object IDs and ownership IDs.
6. Object map updates ownership and endpoint relationship data.

### 10.5 Attack Trigger
The user can trigger testing via:
- Right-click request -> Test IDOR (All Actors)
- Right-click request -> Run Mutation Set
- Right-click request -> Focus Mode
- Right-click request -> Attack Simulation Mode
- Bulk run from Object Map or Findings tab

### 10.6 Replay
1. ACAS identifies candidate objects in the request.
2. ACAS selects alternate actors.
3. ACAS applies session swap.
4. ACAS generates mutation variants.
5. ACAS replays requests.
6. ACAS stores request/response pairs.

### 10.7 Analysis
1. Diff engine compares baseline and attack responses.
2. Semantic analysis classifies leak or bypass.
3. Finding is deduplicated and stored.
4. Alert engine optionally sends Telegram/Discord notifications.
5. UI updates with result.

### 10.8 Reporting
1. Findings can be exported as JSON, Markdown, or HTML.
2. Object map can be exported for further triage.
3. Evidence can be sent to Repeater or Intruder.

### 11.5 Relationship Mapping
ACAS should track:

### 11.6 Attack Execution
Modes:
- Focus Mode: one actor against one selected request
- Cross-Actor Mode: all actors against selected request/object
- Attack Simulation Mode: attacker actors against victim objects
- Chaos Mode: random actor/object pairing
- Stealth Mode: only high-confidence candidates and limited mutation count
- Bulk Map Mode: run against all mapped objects of a type

### 11.7 Mutation Engine
Mutation classes should include at minimum:

- Cross-layer pollution (query + body)

- Path extension mutation (.json, .xml, trailing slash)
- Null byte and special char mutation
- Header injection
- Nested array/object mutation
- Broken parameter syntax (userid[]=5)

### 11.8 Response Diffing
Diff engine should compare:
- Status code
- Response length
- Header differences
- Redirect behavior
- Content-type
- JSON field equality/differences
- Presence of sensitive fields
- Similarity score

## 13. Analysis Strategy: Regex and AST

### 13.1 Why Regex
Regex is fast and useful for:
- Numeric ID detection
- UUID detection
- JWT detection
- Common parameter names
- Header token extraction
- Path segment candidate discovery

### 13.2 Why AST
AST-like structured parsing is needed for:
- JSON body traversal
- XML node traversal
- GraphQL variable traversal
- Path-aware mutation generation
- Ownership vs object ID distinction
- Field-level semantic diffing

### 13.3 Hybrid Strategy
Recommended approach:
- Regex pass first for broad candidate detection
- AST pass second for structure and semantic classification
- Merge results into a normalized internal representation

## 19. Endpoint Linking

ACAS should learn producer/consumer patterns.

Examples:
- POST /api/orders -> response contains order_id => producer
- GET /api/order?id=9001 -> request consumes order_id => consumer
- GET /api/orders -> response returns list of order IDs => producer
- DELETE /api/order/9001 -> path consumes order_id => consumer

This allows ACAS to suggest useful attack paths automatically.

## 20. Mutation Engine Specification

### 20.1 Purpose
The mutation engine generates request variants that expose access control weaknesses caused by parser behavior, inconsistent routing, or authorization gaps.

### 20.2 Mutation Categories

#### A. Session Swap
- Same request, alternate actor credentials

#### B. Method Mutation
- GET -> POST
- GET -> HEAD
- GET -> PUT
- POST -> PATCH
- POST -> DELETE

#### C. Parameter Pollution
- Duplicate same parameter in query
- Duplicate same parameter in body
- Attacker value first, victim value second
- Victim value first, attacker value second

#### D. JSON Structure Mutation
- Scalar to array
- Scalar to object
- Nested object wrapping
- Null value
- Empty string
- Wildcard
- Duplicate keys where serializer allows

#### E. Key Mutation
- user_id -> User_Id
- user_id -> userId
- user_id -> USER_ID
- id -> ID
- dotted and hyphenated variants

#### F. Value Type Mutation
- number to string
- string to array
- float-like numeric
- URL encoded value
- double encoded value
- unicode escaped value

#### G. Path Mutation
- Trailing slash
- Double slash
- .json
- .xml
- .html
- encoded separators
- version path changes
- legacy path variants

#### H. Null Byte / Special Character
- %00
- %00 suffix
- semicolon suffix
- quote or backtick suffix

#### I. Header Injection
- X-Original-URL
- X-Rewrite-URL
- X-Forwarded-For
- X-User-Id
- X-Account-Id
- custom auth bypass headers

#### J. Array / Framework Syntax Mutation
- userid[]=5
- userid[0]=5
- user[id]=5
- NoSQL style operators if relevant

### 20.3 Smart Filtering
Do not run all mutations for all requests.

Use request fingerprinting to select relevant mutations based on:
- Content-type
- Parameter style
- Path style
- Backend hints
- Whether value is numeric, UUID, or string
- Whether endpoint appears legacy or versioned

### 20.4 Mutation Metadata
Each mutation should track:
- Mutation ID
- Mutation class
- Description
- Risk level
- Applied location
- Original value
- Mutated value
- Serialization notes

## 22. Response Diff Engine

### 22.1 Surface-Level Checks
- Same status code as owner baseline
- Similar response size
- Same redirect chain pattern
- Same content-type
- Header similarity

### 22.2 Semantic Checks
- Same sensitive fields present
- Same object IDs returned
- Same nested fields present
- Partial overlap of owner data
- Error message mismatch indicating hidden success

### 22.3 Leak Categories
- Full object leak
- Partial object leak
- Metadata leak only
- Hidden success state
- Privileged action success

### 22.4 Confidence Strategy
Higher confidence when:
- Non-owner receives 200 where owner receives 200 and expected block is absent
- Sensitive fields match baseline
- Response contains owner object values
- Repeatedly reproducible across retries

## 29. Security and Privacy Considerations

Because ACAS stores credentials and tokens, the tool itself becomes sensitive.

Requirements:
- Mask secrets in UI by default
- Avoid plaintext export unless user explicitly chooses it
- Optionally encrypt persisted config
- Never send secrets in Telegram/Discord alerts
- Avoid accidentally alerting request bodies with passwords
- Respect legal/engagement scope
- Add warning banner that user is responsible for authorized testing only

---

## 30. Performance Considerations

Challenges:
- Burp traffic can be noisy
- Mutation counts can explode combinatorially
- Large APIs may create huge object maps

Recommended controls:
- Scope filtering first
- Confidence thresholds before full mutation run
- Maximum mutations per request
- Maximum concurrent replays
- Dedup object values
- Cache baseline responses
- Only AST-parse bodies of relevant content-types
- Lazy UI refresh for large tables

## 38. Example Use Cases

### Use Case 1: Standard IDOR
- victim_1 retrieves order 9001
- ACAS maps owner -> order_id 9001
- attacker_1 replays same request
- response still returns order details
- finding = FULL_IDOR

### Use Case 2: Partial Data Leak
- attacker_1 gets masked response but still sees victim email and invoice amount
- finding = PARTIAL_DATA_LEAK

### Use Case 3: Method Bypass
- GET is blocked
- POST to same endpoint succeeds
- finding = METHOD_BYPASS

### Use Case 4: Parameter Pollution
- ?user_id=attacker&user_id=victim causes victim object to load
- finding = POLLUTION_BYPASS

### Use Case 5: Header Trust
- X-User-Id or X-Original-URL changes authorization behavior
- finding = HEADER_TRUST_BYPASS

## 39. Risks and Pitfalls

- Over-testing can trigger rate limits or bans
- Parsing too aggressively can create noise and false positives
- Storing sessions insecurely can create tool risk
- Too many mutations can reduce signal-to-noise ratio
- Supporting every framework-specific parser edge case is difficult
- UI complexity can become overwhelming if not phased well

Mitigation:
- Strong defaults
- Scope limits
- Confidence scoring
- Mutation caps
- Deduplication
- Clear UX modes

## 41. Definition of MVP Done

MVP is complete when:
- User can add at least 2 actors
- ACAS can capture in-scope traffic
- ACAS can map at least one object type to one actor
- User can right-click request and replay as all other actors
- ACAS can compare baseline vs replay result
- ACAS can generate and store at least one finding type
- ACAS displays actors, object map, and findings in UI
- Project state can be saved and loaded

## 43. Final Product Positioning

ACAS is not just a Burp helper.
It is a structured access control testing platform that models identities, ownership, parser behavior, and attack paths in a single workflow.

Its value lies in turning a deeply manual testing problem into a repeatable system that:
- learns context,
- preserves ownership mapping,
- generates realistic attack variants,
- and produces actionable findings with evidence.

## 44. Final Recommendation

Build ACAS in phases, but keep the architecture modular from day one.

The strongest path is:
1. Burp extension MVP with actor management, scope, mapping, replay, and findings.
2. Add AST-aware mapping and semantic diffing.
3. Add mutation engine and alerting.
4. Add optional dashboard after the extension workflow is solid.

This will keep delivery realistic while preserving the long-term vision.
